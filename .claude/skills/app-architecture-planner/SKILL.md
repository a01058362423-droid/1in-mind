# 솔로 개발자를 위한 아키텍처 설계

혼자 만들고 혼자 운영(배포, 모니터링, 디버깅)할 것을 전제로 아키텍처를 설계한다. 최적의 아키텍처가 아니라 "혼자서 유지보수 가능한" 아키텍처를 우선한다.

## 판단 기준 (이 순서로 우선순위)

1. **운영 부담 최소화**: 관리형 서비스(managed) > 직접 운영. 혼자서 새벽에 서버가 죽어도 대응 못 하는 상황을 피한다.
2. **속도 우선, 나중에 최적화**: 지금 아는 도구, 검증된 보일러플레이트를 우선. 새로운 기술 학습 비용이 스코프에 안 맞으면 지양.
3. **비용 예측 가능성**: 트래픽이 갑자기 늘어도 예상 밖의 청구서가 나오지 않는 구조(사용량 상한, 알림) 확인.
4. **확장은 필요해지면**: 지금 필요 없는 확장성(MSA, 멀티 리전 등)을 미리 설계하지 않는다.

## 산출물

다음을 정리해서 제시한다:

- **스택 제안**: 프론트엔드 / 백엔드 / DB / 인증 / 배포·호스팅 / 결제(필요시) — 각각 왜 이 선택인지 1줄 이유.
- **데이터 모델 초안**: 핵심 엔티티와 관계를 간단히 (ERD 텍스트 설명 또는 간단한 다이어그램).
- **하지 않을 것**: 지금 단계에서 의도적으로 배제하는 기술/패턴과 이유 (예: "지금은 마이크로서비스 안 함 — 트래픽 근거 없음").
- **가장 위험한 기술적 가정**: 검증 안 되면 나중에 크게 다시 만들어야 할 부분 1~2개와 미리 검증하는 방법.

## 주의

사용자의 기존 코드베이스나 이미 정해진 스택이 있다면 그것을 최우선으로 존중하고, 새 스택을 처음부터 제안하지 않는다. 먼저 리포지토리에 기존 기술 스택 흔적이 있는지 확인한다.
